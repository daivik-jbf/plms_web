# Decisions

Dated entries, newest last. Each has the reason. The spec (`docs/superpowers/specs/2026-10-08-jbf-lms-portal-design.md`) holds the product decisions in full; they are repeated here so this file is a complete log.

## Product decisions (from discovery and the spec)

- **2026-10-08: Single organization.** One shared library for JBF. Reason: the deployment serves one organization of about 50 users; multi-tenancy would add cost and risk for no benefit.
- **2026-10-08: Admin and Staff only.** No learner accounts, no third parties. Reason: only staff use the portal and the mobile app in version 1, so two roles keep permissions simple to enforce and test.
- **2026-10-08: Staff can edit but not delete.** Staff can upload and edit content; only Admins delete, restore and purge. Reason: limits the damage a mistaken or compromised Staff account can do.
- **2026-10-08: Trash is a soft delete.** Deleting moves content to Trash; only Admins restore or purge. Reason: accidental deletion must be reversible.
- **2026-10-08: Option 2 stack: React + NestJS + PostgreSQL + S3-compatible storage.** Reason: a conventional, well-supported stack that one small team can maintain, with a typed API that the mobile app can consume and storage that scales without a rebuild.
- **2026-10-08: MP4-only in version 1.** H.264/AAC, no transcoding. Reason: transcoding is costly and complex; the content team can prepare MP4 files.
- **2026-10-08: Offline downloads are visible in the device file manager and unprotected.** No encryption or expiry. Reason: a product decision for version 1; the consequence (files cannot be revoked after deactivation) is accepted and recorded in the spec.
- **2026-10-08: Email-invite login, no self-signup, no 2FA yet.** Reason: Admins control exactly who has an account; two-factor authentication is out of scope for version 1.

## Engineering decisions (milestone 1)

- **2026-10-08: Drizzle over Prisma.** Reason: SQL-like queries, plain versioned SQL migrations, and it is easy to add custom migrations for the audit triggers.
- **2026-10-08: npm workspaces instead of pnpm.** Reason: Homebrew's pnpm depends on a different Node major than Node 24.
- **2026-10-08: Node 24 LTS.** Reason: the current long-term-support line, pinned in `.nvmrc` and `engines`.
- **2026-10-08: NestJS pinned to the 11 line.** Reason: NestJS 12 is ESM-only and breaks the CommonJS Jest setup.
- **2026-10-08: TypeScript 6 tsconfig uses `module: commonjs` with `moduleResolution: bundler`.** Reason: TypeScript 6 rejects `moduleResolution: node`, and `bundler` is the setting that still works with CommonJS output.
- **2026-10-08: Jest transpiles jose 6 through `apps/api/tsconfig.jest.json`.** Reason: jose 6 is ESM-only, so Jest has to transform it (`transformIgnorePatterns` lets `jose` through) for the CommonJS tests to import it.
- **2026-10-08: The access check hits the database on every request.** Reason: deactivation and role changes apply immediately instead of waiting for a 15-minute token to expire. The cost is one indexed lookup per request, which is fine at this scale.
- **2026-10-08: Web and API must be served from the same origin** (one host name, with a reverse proxy sending `/api` to the API). Reason: as built, the web app calls the API with relative `/api/...` URLs, and the refresh cookie is `SameSite=Strict` with path `/api/auth`. Separate `app.` and `api.` subdomains would need a `VITE_API_BASE` setting and CORS with credentials; that is future work.
- **2026-10-08: Audit append-only is enforced by database triggers now; the restricted database role (INSERT and SELECT only) is deferred to milestone 7.** Reason: triggers already block updates and deletes for every role, which makes tampering evident against the table owner; the separate role belongs with deployment hardening, when production roles exist.
- **2026-10-08: Shared types package deferred.** Reason: nothing in milestone 1 needs it, and an empty package would be unused structure. Add it when a milestone needs types in both web and API.
- **2026-10-08: Password blocklist derived from the SecLists NCSC 100k list, filtered by byte length to roughly 10+ characters (49 non-ASCII entries are shorter; harmless).** Source: `Passwords/Common-Credentials/100k-most-used-passwords-NCSC.txt` in the SecLists project (https://github.com/danielmiessler/SecLists), which is published under the MIT licence; the list is lower-cased and de-duplicated. The build sandbox blocked the download, so a copy fetched earlier from the same URL was used. Reason: the length rule already rejects short passwords, so only the entries that could pass it are worth keeping.
- **2026-10-08: In-memory rate limiting.** Reason: simplest option for one API instance. Move the counters to a shared store (for example Redis or the database) if the API is ever scaled to several instances.
- **2026-10-08: OpenAPI document deferred; `docs/api/auth.md` is written by hand for now.** Reason: the mobile developer needs the contract now, and generating a full OpenAPI document is better done once, alongside the sync endpoints in milestone 6. Pending the user's confirmation (see `PROGRESS.md`).
- **2026-10-08: Added the design token `--color-border-strong` (`#6b8794`).** Reason: input borders must meet a 3:1 contrast ratio against the background (WCAG 2.1 non-text contrast); the original light border did not.
- **2026-10-08: A locked real account answers 429 while an unknown email answers 401.** Reason: a clear lockout message helps real users. Consequence: account existence can be inferred after 5 wrong guesses; accepted, and slowed by the per-IP rate limit.
- **2026-10-08: A refresh 401 does not clear the web cookie, and the web app serialises refresh across tabs with the Web Locks API.** Reason: with rotating refresh tokens, two tabs refreshing at once used to sign each other out when the losing request cleared the cookie the winner had just set.
- **2026-10-08: Lock order for sessions: user row first, then refresh token rows; password reset rows before the user row.** Reason: a refresh takes the user row `FOR SHARE` before it rotates its token, so a password change, reset or deactivation (which update or lock the user row before revoking tokens) can never miss a freshly rotated token, and a fixed order avoids deadlocks. Forgot-password requests for one user are serialised with a transaction advisory lock instead of a user row lock.

## Engineering decisions (milestone 2)

- **2026-10-08: The Staff page has two tabs, People and Invites.** Reason: people and invites are different lists with different actions; tabs keep each table short and the page easy to scan, with counts on the tab labels.
- **2026-10-08: Audit details open in a side drawer** (full width on phones), not inline in the row. Reason: the full record is long (changes table, IP, request id), and a drawer keeps the table's rows aligned and lets Esc return focus to the row.
- **2026-10-08: "Viewed audit log" is logged once per page open** (`POST /api/audit/opened`), not on every request, filter or page change. Reason: logging every read would bury the log in noise; one entry per visit still answers "who looked at the log, and when". The server cannot tell a page open from a filter change on `GET /api/audit`, so the page announces the open itself.
- **2026-10-08: Keyset paging with microsecond-exact cursors** (`occurred_at` then `id`, newest first), not offset paging. Reason: the log keeps growing while someone reads it; offsets would shift, repeat or skip rows. Cursors carry the database's own timestamp text, because a JavaScript Date only has millisecond precision and would skip or repeat rows that share a millisecond.
- **2026-10-08: The cursor carries Postgres microsecond text rather than a JS Date, and is validated for calendar and clock ranges.** Reason: a Date loses microseconds. A cursor that matched the shape but was not a real time (`2026-02-30`, `24:00:00`) used to reach Postgres, which rejected it as a 500; it is now a 400 with `fieldErrors.cursor`, and the database error is also translated as a second guard.
- **2026-10-08: The paging index is declared `DESC NULLS LAST` and the list query orders `DESC NULLS LAST`.** Reason: Postgres only uses an index whose sort order matches the query exactly. The first version declared one order and queried the other, so the index was silently unused (found with EXPLAIN); the two now match.
- **2026-10-08: Summaries are generated on the server.** Reason: the web portal and the mobile app show the same plain-English sentence, wording is fixed in one tested place, and a new action cannot reach one client untranslated.
- **2026-10-08: Names are joined at read time** (users table joined when the log is read); the log still stores the email label as it was at the time. Reason: the log should show the person's name as it is in the users table (names are not editable today, so this is the name they were given at invite), and an email label alone is hard to read; the stored label keeps what was recorded at the time. Consequence: names stop resolving if users are ever hard-deleted (today they are only deactivated); recorded as an open item.
- **2026-10-08: The export has a cap (`AUDIT_EXPORT_MAX_ROWS`, default 50,000, otherwise 413) and neutralizes spreadsheet formulas.** Reason: an unbounded export can exhaust the server and a huge file is not useful to open; failed sign-ins store text typed by anyone, so a cell starting with `=`, `+`, `-`, `@`, tab, CR or LF gets a leading apostrophe so Excel and Sheets do not run it. The file is streamed in chunks of 1,000 rows.
- **2026-10-08: The export uses a database-clock snapshot (`clock_timestamp()`).** Reason: the export records its own `audit.exported` entry, and other activity continues during a long download. Taking one snapshot time first and using it for the cap check, the recorded `rowCount` and the streamed rows makes them one set; without it the file could contain its own audit row and exceed the cap by one, with a wrong recorded count.
- **2026-10-08: Dialogs and drawers use the native `<dialog>` with `closedby="any"`, and a click-outside fallback for browsers without it (Safari).** Reason: the browser provides focus trapping, Esc and the top layer for free and accessibly; the fallback keeps behaviour the same in Safari.
- **2026-10-08: `Dialog` has a `blocked` prop that prevents closing while a request is in flight, and `perform()` falls back to a page notice if the dialog it started from has closed.** Reason: dismissing a dialog mid-request lost the server's answer and could show a "last Admin" error inside the next dialog. Blocking closes the common path; the fallback covers browsers that still let a second Esc through, so a result is never lost or shown in the wrong place.
- **2026-10-08: The Audit page ignores a late "Load more" after the filters change, using a generation counter.** Reason: a slow "Load more" response for the old filters must not overwrite the list for the new filters.
- **2026-10-08: Row actions are inline buttons, not a row menu.** Reason: simpler and more accessible (every action is a visible, focusable button; no menu keyboard handling to build and test). Planned simplification of the spec, noted in the plan.
- **2026-10-08: No top-bar search yet.** Reason: there is no content to search until later milestones; an empty search box would be a dead control.
- **2026-10-08: The sign-out notice is carried in auth state** (`signOut(notice?)` stores it on the anonymous state, and the sign-in screen reads it). Reason: after a password change the person lands on the sign-in screen and should be told why; auth state survives the redirect without putting a message in the URL or in storage.
- **2026-10-08: Admin-only pages are hidden in the UI and enforced by the server.** Reason: the sidebar hides Staff and Audit log for Staff and an Admin route sends them to the Dashboard, which is a convenience; the real rule is the server's 401 and 403 on every audit, user and invite route.


## Engineering decisions (milestone 3)

- **2026-10-09: Cloudflare R2 for file storage.** Reason: R2 does not charge for data leaving the bucket, which suits many phones downloading videos; it is S3-compatible, so the code (the AWS SDK) stays portable to another S3 service if needed.
- **2026-10-09: Videos are limited to 2 GiB and MP4 only.** Reason: the tighter limit (the parent spec proposed 4 GB) keeps uploads and storage costs manageable, and MP4 (H.264/AAC) plays in every browser and phone without transcoding, which this system does not do.
- **2026-10-09: The browser uploads straight to storage in 16 MiB pieces; the API never carries video bytes.** Reason: the API stays small and fast, pieces give retry and resume on slow or unreliable connections, and 5 MiB is the storage minimum for every piece except the last (16 MiB fixed pieces also satisfy R2's rule that pieces are the same size, and give at most 128 pieces for 2 GiB).
- **2026-10-09: Three storage drivers: R2, a local development driver and an in-memory test driver. The local driver is refused in production, and `npm run storage:check` is the only proof against the real R2.** Reason: the whole flow can be built and tested before a Cloudflare account exists, but a stand-in cannot prove Cloudflare's behaviour (checksums, CORS, receipts), so the check script exists to do that once credentials are available.
- **2026-10-09: The local driver serves files through public `/api/dev-storage/*` routes with HMAC-signed, expiring, single-operation links; the routes answer 404 unless the local driver is active; the signing secret is random at start-up if `STORAGE_SIGNING_SECRET` is not set; the request logger redacts those paths.** Reason: it mimics R2's temporary links closely enough to exercise the same code, existing `.env` files keep working, links never reach the logs, and the production environment check makes sure none of it exists in production.
- **2026-10-09: Completion verifies size, type and first bytes on the server and discards a mismatch.** Reason: the browser's declaration (size, type) cannot be trusted; a lying or corrupt file is deleted, its rows removed, `file.upload_failed` is recorded and the person gets a plain 422.
- **2026-10-09: Completion is idempotent and recovers when storage finished but the database did not.** Reason: a network failure or a second click must not leave a stuck or duplicated video; if storage already joined the pieces, completion carries on and judges what is stored.
- **2026-10-09: Cancel, failure and cleanup remove the database rows first, conditionally on the upload still being pending, then storage.** Reason: a video that became ready a moment earlier can never be removed by them, and a leftover object in storage is harmless and tidied by cleanup.
- **2026-10-09: Lock order for media rows is the `media_items` row before the `files` row, everywhere.** Reason: a real deadlock between an upload finishing and a cancel was found during the build and fixed; one fixed order makes finish, cancel, cover replacement and cleanup safe against each other.
- **2026-10-09: Completion treats an object that vanished (a cancel or cleanup racing the verification) as 404 or 409, never 500.** Reason: it is an expected race, not a server fault, and the person should get a message they can act on.
- **2026-10-09: A video is invisible to everyone but its uploader (including Admins) until it is ready.** Reason: half-uploaded or rejected files must never appear to other people; an Admin who needs to clear a stuck upload may still cancel it through the upload routes.
- **2026-10-09: Every playback link issued is audited, including renewals.** Reason: the audit log should show every time a link to a video was handed out; "Changes only" hides these entries by default so they do not bury real changes.
- **2026-10-09: Cover completion is `POST /api/media/items/:id/cover/:fileId/complete`, not the spec's `POST /covers/:fileId/complete`.** Reason: carrying the item id in the path means a pending cover file needs no extra column to know which item it belongs to.
- **2026-10-09: A cover upload link is signed over its content type (`signableHeaders: content-type`), so the browser must send exactly the declared `Content-Type`, and the bucket's CORS `AllowedHeaders` must include `Content-Type`.** Reason: the SDK leaves the type out of the signature by default; binding the link to the declared type means a cover cannot be uploaded as another type. `storage:check` verifies `access-control-allow-headers`.
- **2026-10-09: ACCEPTED RISK (ruling R8): a cover upload link (valid one hour, signed over the content type but not the length) stays usable after the cover is verified.** Whoever obtained the link can overwrite the stored cover object, bypassing the size and first-bytes checks, until the link expires. Only a signed-in Staff or Admin can obtain such a link, links force the declared content type when read, and the bucket is private. Reason for accepting it: closing it needs a server-side copy of the file on completion, which is more machinery than this milestone warrants; it is recorded in `docs/storage.md` and can be done later.
- **2026-10-09: `storage:check` aborts its test multipart uploads, reports the HTTP status of its test upload before judging CORS, and reduces `WEB_ORIGIN` to an origin.** Reason: the script must leave nothing behind, a refused upload (wrong key or bucket) would otherwise be reported as a misleading CORS problem, and a `WEB_ORIGIN` with a path or trailing slash would never match the origin a browser sends.
- **2026-10-09: The upload manager offers Cancel only while an upload is sending, not while it is finishing.** Reason: cancelling during the server's completion could mark a good upload as failed.
- **2026-10-09: A replaced cover file is deleted from storage; it is the only deletion in this milestone.** Reason: an orphaned cover is waste nobody can reach; deleting videos waits for the Trash in milestone 6.
- **2026-10-09: The upload manager keeps its state in memory only, so a reload ends the sending; the folder page then offers Resume from the server's record of unfinished uploads.** Reason: nothing sensitive (links, file contents) is persisted in the browser, and the server already knows which pieces exist, so resuming needs only the same file.
- **2026-10-09: The abandoned-upload cleanup is an in-process hourly timer plus the `storage:cleanup` command.** Reason: it is the simplest thing that works for one API instance, and running it twice is harmless; with several API instances it would need a shared lock or a separate scheduled job.
